# KBO 수집 대상과 실행 범위

결정일: **2026-08-26 (Asia/Seoul)**

상태: **프로젝트 확정 범위**

이 문서는 Inning Log 경기 수집기의 제품 범위를 고정한다. 대화나 개인 메모보다 이 문서를 우선하며, 범위를 바꿀 때에는 코드와 정책 검사를 수정하기 전에 이 문서부터 변경한다.

## 1. 확정한 제공처와 페이지

운영 대상은 KBO 홈페이지의 다음 두 페이지뿐이다.

| 용도 | 허용 후보 페이지 | 필요한 값 |
| --- | --- | --- |
| 일정·취소·연기 확인 | [KBO 경기일정·결과](https://www.koreabaseball.com/Schedule/Schedule.aspx) | 경기 일자, 예정 시각, 홈·원정팀, 구장, 예정·취소·연기 상태 |
| 경기 진행 확인 | [KBO 스코어보드](https://www.koreabaseball.com/Schedule/ScoreBoard.aspx) | 홈·원정 점수, 경기 상태, 현재 이닝과 초·말, 표시되는 경우 실제 시작·종료 시각 |

다음 대상은 운영 범위에서 제외한다.

- NAVER 스포츠 웹 페이지와 API
- KBO 게임센터·문자중계·기록실·선수 페이지
- 개발자 도구나 자바스크립트에서 발견한 내부 JSON·ASMX endpoint
- 경기별 상세 relay, 타석 원문, 기사, 하이라이트, 이미지와 영상
- 로그인, 쿠키, 세션, CAPTCHA, 우회용 프록시가 필요한 경로

저장소에 과거 회귀 테스트용 NAVER adapter나 KBO 내부 endpoint 설정이 남아 있더라도 배포 대상이나 허용 범위로 해석하지 않는다. Fargate 배포 진입점은 `src/fargate/main.js`, 설정은 `config/fargate.yml`이며 이 경로에는 두 고정 페이지 외의 URL이나 NAVER adapter가 연결되어 있지 않다. 과거 범용 CLI인 `src/crawler.js`는 Fargate 이미지의 기본 명령과 Scheduler target에서 사용하지 않는다.

## 2. 수집 필드

1차 구현에서 저장할 수 있는 필드는 다음으로 제한한다.

- 경기 일자와 예정 시각
- 홈팀과 원정팀
- 구장
- 경기 상태
- 홈팀과 원정팀의 현재 또는 최종 점수
- 현재 이닝과 초·말
- 페이지에서 명시적으로 확인되는 실제 시작·종료 시각
- 출처 URL, 관측 시각, 내용 지문과 파서 버전

페이지에 값이 없거나 의미가 불분명하면 추정하지 않고 `null` 또는 이상 항목으로 남긴다. 예정 시각을 실제 시작 시각으로 복사하거나 마지막 관측 시각을 종료 시각으로 사용하지 않는다.

### 특별 이벤트

홈런 같은 특별 이벤트는 **2차 범위**다. 1차 배포에는 포함하지 않는다. 추후 필요하면 다음 조건을 모두 다시 검토한다.

1. 두 허용 후보 페이지 안에서 구조화된 사실 값으로 안정적으로 확인할 수 있다.
2. 새로운 페이지, 게임센터, 문자중계 또는 내부 endpoint가 필요하지 않다.
3. 허가 문서가 해당 필드와 사용 방식을 포함한다.
4. 원문 중계 문장을 저장하거나 재현하지 않는다.
5. 별도 fixture, 스키마와 파서 회귀 테스트를 추가한다.

하나라도 충족하지 않으면 이벤트 기능을 추가하지 않는다.

## 3. 실행 주기

한 번의 페이지 응답에 당일 전체 경기가 포함되므로 경기별 요청을 만들지 않는다. 기본 운영안은 다음과 같다.

### 일일 계획 작업

- 매일 `06:00 KST`에 짧은 계획 작업을 한 번 실행한다.
- `Schedule.aspx` 한 번에서 화면에 표시된 월 전체 일정·결과를 동기화한다.
- 월 전체 데이터 중 당일 경기만 분리해 경기 작업 실행 시각을 계산한다.
- 경기가 없으면 상태만 기록하고 종료한다.
- 경기가 있으면 가장 이른 예정 시각 60분 전에 경기 작업이 시작되도록 일회성 스케줄을 만든다.
- 계획 작업 실패 시 공격적으로 반복하지 않고 최대 2회까지만 재시도한 뒤 DLQ와 알림으로 전환한다.

### 경기 시간대 작업

- 시작 직후 `Schedule.aspx`를 다시 확인해 당일 취소·연기·시간 변경을 반영한다.
- 미종료 경기가 있는 동안 일정 페이지는 기본 15분 간격으로 확인한다.
- `ScoreBoard.aspx`는 가장 이른 예정 시각 10분 전부터 확인한다.
- 실제 진행 경기가 있으면 기본 2분 간격으로 스코어보드 한 페이지만 확인한다.
- 모든 경기가 취소·연기되면 점수 요청을 중단하고 종료한다.
- 모든 경기가 종료되면 5분, 30분, 90분 뒤 최종 보정 확인을 하고 종료한다.
- 프로세스에는 12시간의 하드 타임아웃을 두어 영구 실행을 막는다.

폴링 간격은 허가된 호출량이 더 낮다면 그 범위에 맞춰 늘린다. `ETag`와 `Last-Modified`가 제공되는 경우 조건부 요청을 사용한다. 401·403·429, CAPTCHA, robots 변경과 명시적 차단 문구는 간격 조정 대상이 아니라 즉시 중단 신호다.

## 4. AWS 실행 모델

배포 모델은 같은 컨테이너 이미지의 두 실행 모드로 나눈다.

```text
매일 06:00 EventBridge Scheduler
              │
              ▼
       Fargate 계획 작업
       Schedule.aspx 1회
       표시 월 전체 저장
              │
              ├── 경기 없음 ──> 종료
              │
              └── 경기 있음 ──> 일회성 실행 예약
                                  │
                                  ▼
                           Fargate 경기 작업
                           일정 재확인 + ScoreBoard 폴링
                                  │
                                  ▼
                           정규화 결과 전달 후 종료
```

계획 작업과 경기 작업은 동시에 하나씩만 실행한다. DynamoDB 조건부 쓰기로 lease를 잡고, 동일 날짜·동일 경기의 중복 결과는 내용 지문으로 제거한다.

구체적인 AWS 콘솔 설정은 [AWS_FARGATE_SETUP.md](./AWS_FARGATE_SETUP.md)를 따른다.

## 5. 정책 게이트

이 두 페이지가 로그인 없이 보이고 필요한 값이 표시된다는 사실은 자동 수집 허가가 아니다. [POLICY.md](./POLICY.md)의 현재 `BLOCK` 판정은 그대로 유지한다.

실 네트워크를 열려면 최소한 다음 범위가 서면으로 확인되어야 한다.

- 호스트: `www.koreabaseball.com`
- 경로: `/Schedule/Schedule.aspx`, `/Schedule/ScoreBoard.aspx`
- 메서드와 필요한 날짜 선택 방식
- 일정 페이지와 스코어보드 페이지별 호출 간격·일일 상한
- 위 2절의 저장 필드와 앱 표시·보관·삭제 범위
- robots 전체 차단에 대한 해당 두 경로의 명시적 예외
- 승인 만료일과 중단 요청 연락처

허가가 확보되기 전 AWS에서는 fixture smoke test만 실행한다. 설정값을 임의로 승인 상태로 변경하거나 robots 예외를 꾸며 실제 요청을 보내지 않는다.

## 6. 변경 절차

새 제공처, 새 페이지 또는 새 필드를 추가하려면 다음 순서를 지킨다.

1. 이 문서에 필요성과 정확한 URL·필드를 제안한다.
2. [POLICY.md](./POLICY.md) 기준으로 허가와 정책을 재검토한다.
3. 요청량과 저장·공개 범위를 승인받는다.
4. fixture와 파서 테스트를 먼저 작성한다.
5. 정책 카탈로그와 고정 allowlist를 코드 리뷰로 변경한다.
6. fixture 환경에서 회귀 테스트 후 제한된 운영 검증을 한다.
