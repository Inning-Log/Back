# 크롤러 운영 안내서

이 문서는 크롤러를 안전하게 설정·검증·실행하고 이상 상황에 대응하는 절차다. 제품 범위는 [TARGET_SCOPE.md](./TARGET_SCOPE.md), 정책 판단은 [POLICY.md](./POLICY.md), AWS 운영은 [AWS_FARGATE_SETUP.md](./AWS_FARGATE_SETUP.md)를 기준으로 하며 명령 예시는 `scripts/crawler` 디렉터리에서 실행한다.

## 1. 운영 모드

### Fixture 모드 — 기본 및 권장

외부 서버에 접속하지 않고 저장소의 합성 fixture를 읽는다. 개발, 파서 수정, 병합 검증, UI 연동과 CI는 모두 이 모드에서 수행한다.

```bash
npm run config:check -- --profile fixture
npm run crawl -- --profile fixture --dry-run
npm run crawl -- --profile fixture
```

### 실 네트워크 모드 — 기본 차단

과거 `safe`와 `hybrid-locked`는 범용 CLI의 차단 회귀 테스트용일 뿐 운영하지 않는다. 실제 배포 대상은 `src/fargate/main.js`와 `config/fargate.yml`의 `kbo-live`이며, 기본 상태에서는 `kbo-locked`가 이름 그대로 실행 불가입니다. 실제 환경은 `kbo-live` 프로필로 전환해서만 허용합니다.

실행 전 매번 다음 순서로 확인한다.

1. 허가 문서의 유효기간과 허용 호스트·경로·필드·호출량을 대조한다.
2. 공식 약관과 robots.txt를 새로 확인하고 결과를 증빙에 기록한다.
3. 비밀이 제거된 유효 설정을 출력해 승인 범위와 비교한다.
4. 정책 검사와 dry-run에서 외부 요청 계획을 검토한다.
5. 최소 날짜·최소 경기 수로 1회 실행하고 지표를 확인한다.
6. 정상일 때만 스케줄 실행을 허용한다.

```bash
npm run fargate:config:check -- --profile kbo-locked --print-config
npm run fargate:policy:check -- --profile kbo-locked
npm run fargate:plan -- --profile kbo-locked --dry-run
```

저장소의 `kbo-locked`는 `enabled: false`, 승인 `unverified`, `killSwitch: true`이므로 현재 정책 검사는 의도적으로 `BLOCK`과 exit code `2`가 된다. dry-run은 이 상태에서도 외부 요청 `0`으로 계획과 고정 URL만 보여 준다. 정책 검사에 실패하면 설정을 우회하거나 검사 코드를 끄지 않는다.

실제 허가가 완료되면 같은 절차를 `kbo-live`로 반복하고, 추가로 아래를 확인한다.

```bash
npm run fargate:config:check -- --profile kbo-live --print-config
npm run fargate:policy:check -- --profile kbo-live
npm run fargate:plan -- --profile kbo-live --dry-run
```

`--check-policy`는 네트워크 없는 사전 검사다. 승인 상태·증빙 식별자·scope·최근 검토 시각·만료와 robots 예외 기록을 검증한다. Fargate 실행의 네트워크 범위를 정확히 두 페이지로 유지하기 위해 런타임이 robots URL을 세 번째로 요청하지는 않는다. 운영자가 활성화 직전 공식 robots 원문을 다시 확인하고, 7일 이내 검토 시각과 두 경로의 서면 예외를 설정해야 한다. 해당 기록이 오래됐거나 없으면 두 페이지 요청 전 정책 게이트가 차단한다.

## 2. 시작 전 체크리스트

- [ ] `npm run config:check`가 성공한다.
- [ ] 현재 설정에서 네트워크 사용 여부와 대상 URL이 예상과 같다.
- [ ] fixture가 실제 서비스 응답·중계 문장을 복제하지 않은 합성 데이터다.
- [ ] 실 네트워크라면 유효한 서면 허가와 정책 스냅샷이 있다.
- [ ] 허가의 호스트·경로·필드·요청량·보존·재배포 범위가 설정보다 넓거나 같다.
- [ ] KBO 약관·robots.txt 변경 여부를 재확인했다.
- [ ] KBO 차단에서 `Schedule.aspx`와 `ScoreBoard.aspx`를 예외로 하는 `robots-disallow-override` 서면 범위가 있다.
- [ ] 요청 URL이 위 두 페이지뿐이고 NAVER·게임센터·문자중계·내부 endpoint가 포함되지 않는다.
- [ ] 상세 이벤트와 설명 원문이 비활성 상태다.
- [ ] User-Agent의 프로젝트 식별자와 연락처가 승인 내용과 일치한다.
- [ ] kill switch가 즉시 작동하는지 담당자가 알고 있다.
- [ ] 출력·로그에 원문 relay, 로고·영상, 쿠키·토큰이 포함되지 않는다.
- [ ] 데이터 보존 만료 및 삭제 책임자가 정해져 있다.

## 3. 설정 변경 절차

공용 기본값은 `config/crawler.yml`에서 관리한다. 비밀이나 개인별 임시 값은 커밋하지 않는다.

1. YAML의 `base`에는 모든 환경에 적용할 보수적 기본값을 둔다.
2. `profiles.fixture`에는 네트워크를 사용하지 않는 개발·테스트 설정을 둔다.
3. 범용 CLI의 `profiles.safe`, `profiles.hybrid-locked`는 과거 구조 차단 회귀용으로만 유지한다.
4. KBO 두 페이지 전용 profile은 승인 전에는 `config/fargate.yml`의 `kbo-locked`로 확인하고, 승인 후에는 `kbo-live`를 사용한다. URL은 코드 상수이므로 환경변수로 교체할 수 없다.
5. 허가 후 저부하 제한과 승인 식별자는 저장소 밖 환경 파일이나 환경변수로 주입한다.
6. 한 번의 실행에만 필요한 값은 명시적 CLI 옵션 또는 `--set`으로 덮어쓴다.
7. 변경 뒤 `--check-config`, `--print-config`, `--check-policy`, `--dry-run` 순으로 검증한다.

유효 설정의 우선순위는 낮은 쪽부터 다음과 같다.

```text
config/crawler.yml의 base
  < 선택한 profiles.<profile>
  < env-file
  < 프로세스 환경변수
  < 명시적 CLI 옵션과 --set
```

`--print-config` 출력은 토큰·쿠키 등 비밀값이 가려져야 한다. 가려지지 않는 비밀을 발견하면 화면 공유나 로그 첨부를 중단하고 이슈로 등록한다.

## 4. 폴링과 부하 제어

상태별로 필요한 새로움이 다르므로 고정된 짧은 주기를 쓰지 않는다.

| 경기 상태 | 운영 원칙 |
| --- | --- |
| 일일 계획 | 06:00 KST에 일정 페이지 1회, 경기 없으면 종료 |
| 당일 예정 | 경기 Task 시작 시 일정 재확인, 스코어보드는 가장 이른 시작 10분 전부터 |
| 진행 중 | 일정 페이지 기본 15분, 스코어보드 페이지 기본 2분. 각 주기마다 당일 전체 경기를 한 요청으로 처리 |
| 지연·중단 | 일정 확인을 유지하고 스코어보드는 기본 5분으로 늘림 |
| 종료 | 종료 후 5분·30분·90분 시점에 최대 3회 최종 확인하고 종료 |
| 취소·연기 | 모든 경기가 취소·연기되면 스코어보드 요청을 중단하고 Task 종료 |

위 값은 현재 스케줄러의 **요청 가능 시각** 기본값이다. 실제 허가서의 최소 간격이 더 길면 반드시 허가서 값을 따른다. 실제 폴링 간격은 cron 기동 간격보다 짧아질 수 없으므로, 기본 cron `*/5 * * * *`에서는 1분 eligibility도 최대 5분마다만 평가된다. 반대로 cron이 더 자주 실행되더라도 스케줄러가 경기별 다음 허용 시각을 확인해 불필요한 요청을 생략한다.

요청 스케줄러는 다음을 지켜야 한다.

- 동일 URL과 동일 경기 요청을 합쳐 중복 호출하지 않는다.
- 상세 데이터는 상태가 바뀌었거나 TTL이 만료된 경기만 조회한다.
- 경기 상태와 마지막 폴링 시각으로 다음 eligibility를 계산하고, 내용이 같으면 파일 재기록을 생략한다.
- 조건부 요청을 사용할 수 있으면 `ETag`/`If-None-Match`, `Last-Modified`/`If-Modified-Since`를 사용한다.
- 백오프에는 jitter를 넣어 여러 인스턴스가 동시에 재시도하지 않게 한다.

현재 `maxRequestsPerRun`과 `maxAttemptsPerRun`은 **실행당** 상한이며 프로세스가 다시 시작되면 초기화된다. 스냅샷과 경기별 폴링 시각은 `.crawler-state.json`에 남지만, HTTP 조건부 요청 validator와 circuit 상태는 프로세스 메모리에만 있다. 허가서가 시간당·일일 총량을 정한다면 단일 인스턴스만 실행하고 배포 계층의 영속 rate limiter·모니터링을 추가하기 전에는 실 운영하지 않는다.

실 네트워크 예약 모드는 `output.enabled=true`가 아니면 정책 단계에서 차단된다. `--no-write`로 상태 저장을 끄면 재시작 후 폴링 시각이 사라져 불필요한 요청을 만들 수 있기 때문이다. 단발성 dry-run과 fixture는 이 제한의 대상이 아니다.

## 5. HTTP 상태별 대응

| 신호 | 즉시 조치 | 재개 조건 |
| --- | --- | --- |
| 401 | 해당 제공처 중지, 인증 정보와 허가 범위 점검 | 공식 인증 절차 및 서면 범위 확인 후 정책 재검사 |
| 403 | 재시도 금지, 제공처 kill switch 활성화 | 제공처의 명시적 해제·허가 확인 후 수동 재개 |
| 404 | URL 추측·열거 금지, 설정 오류로 기록 | 공식 문서 또는 제공처가 올바른 경로를 확인한 경우 |
| 429 | 같은 호출도 자동 재시도하지 않고 신규 요청 중지, `Retry-After` 이상 회로 개방 | 한도 내임을 검증하고 낮은 빈도로 수동 재개; 반복 시 제공처 비활성화 |
| 5xx | 제한된 횟수의 지수 백오프 후 회로 열기 | 충분한 휴지 뒤 단일 점검 요청 성공 |
| timeout/DNS/TLS | 공격적 재시도 금지, 네트워크·인증서 상태 점검 | 원인 해소 뒤 단일 점검 성공 |
| CAPTCHA/차단 문구 | 전체 실 네트워크 즉시 중지 | 우회 없이 제공처의 서면 허가 및 해제 확인 |
| robots/약관 변경 | 실행 중지 및 정책 감사 | 새 정책과 허가 범위 검토 완료 |

401·403·429를 프록시, IP 변경, 헤더 위장, 브라우저 자동화 또는 쿠키 복제로 우회하지 않는다.

## 6. Kill switch

다음 상황에서는 가장 먼저 전체 외부 요청을 차단하고 스케줄러를 내린다.

- 허가 문서가 없거나 만료됐다.
- 정책 검사 또는 robots 검사가 실패했다.
- 예상하지 못한 호스트·경로로 요청하려 한다.
- 401·403·429, CAPTCHA 또는 제공처 경고를 받았다.
- 요청률·동시성·일일 한도가 승인값을 넘었다.
- 원문 relay, 로고, 영상, 개인정보 또는 인증 정보가 출력됐다.
- 데이터 제공처나 프로젝트 책임자가 중단을 요청했다.

중단 후에는 실행 시각, 프로필, 대상 제공처, 마지막 성공 요청, 오류 코드와 영향받은 출력만 기록한다. 토큰·쿠키·원문 응답은 사고 기록에 복사하지 않는다. 자동 재시작을 막고 책임자의 수동 승인 전에는 fixture 이외의 프로필을 재개하지 않는다.

## 7. 삭제 요청 런북

1. 실 네트워크 스케줄과 실행 중 프로세스를 중지하고 kill switch를 켠다.
2. 요청자의 권한과 삭제 범위(제공처, 경기, 날짜, 필드, 파생 데이터)를 확인한다.
3. `out/`, 상태·HTTP 캐시, 로그, 테스트 산출물, CI artifact, 백업, 데모 배포 및 다운스트림 DB를 조사한다.
4. 범위에 속한 원본과 정규화·집계·파생 데이터를 함께 삭제한다.
5. Git에 데이터가 들어갔다면 단순 파일 삭제로 끝내지 말고 저장소 관리자와 이력 정리 및 기존 clone 대응을 협의한다.
6. 재수집 방지 규칙을 추가하고 fixture가 해당 원문을 복제하지 않았는지 확인한다.
7. 데이터 값을 포함하지 않은 처리 기록에 담당자, 범위, 시각, 삭제 위치와 예외를 남긴다.
8. 요청자와 프로젝트 책임자에게 완료 사실을 전달한다.

삭제 범위나 권리자가 불명확하면 임의로 일부만 지우고 재개하지 말고, 전체 수집을 멈춘 상태에서 확인한다.

## 8. 배포 전 점검

- 기본 프로필이 `fixture`인지 확인한다.
- CI와 배포 환경에 실 네트워크 허용값이 들어 있지 않은지 확인한다.
- `.env`, 승인 문서, 토큰, 쿠키와 원본 응답이 Git 추적 대상이 아닌지 확인한다.
- `npm test`와 설정·정책 검사를 통과한다.
- 출력 스키마에서 허용되지 않은 필드가 추가되지 않았는지 확인한다.
- 실제 데이터가 발표·데모·README 예시에 포함되지 않았는지 확인한다.
- 연락 담당자, kill switch와 삭제 런북이 최신인지 확인한다.
