# 크롤링 봇 정책

확인 기준일: **2026-08-25 (Asia/Seoul)**

이 문서는 Inning Log 경기 수집기의 실행 허용 기준이다. 법률 자문을 대신하지 않으며, 프로젝트 내부 기준은 법적으로 가능한 최소선보다 더 보수적으로 운영한다. **학생·비영리·연구 목적이라는 이유만으로 사이트 약관, robots.txt, 저작권, 상표권 또는 접근 제한의 예외가 되지 않는다.**

## 1. 현재 결론

실제 KBO 서버에 대한 자동 요청은 기본적으로 금지한다. 저장소의 기본 프로필은 합성 fixture만 읽으며 외부 네트워크를 사용하지 않는다. 제품 범위는 [TARGET_SCOPE.md](./TARGET_SCOPE.md)에 따라 KBO `Schedule.aspx`와 `ScoreBoard.aspx` 두 페이지만 포함하고 NAVER는 제외한다. 실제 네트워크 수집은 다음 조건을 모두 충족한 뒤에만 허용한다.

1. 데이터 제공 주체로부터 자동 수집을 허용하는 **서면 승낙**을 받았다.
2. 허용 호스트, 경로, HTTP 메서드, 필드, 호출량, 사용 목적, 보관 기간, 공개·재배포 범위와 유효기간이 문서에 구체적으로 적혀 있다.
3. 해당 실행 시점의 이용약관, 서비스 정책, 개발자 문서와 robots.txt를 다시 확인하고 증빙을 남겼다.
4. 실제 설정이 승인 범위를 넘지 않는다는 정책 검사를 통과했다.
5. 운영 책임자와 즉시 중단 수단, 삭제 요청 처리 절차가 정해져 있다.

하나라도 불명확하거나 서로 충돌하면 **실행하지 않는다(fail closed)**. 공개 URL, 브라우저에서 보이는 응답, 인증 없는 HTTP 200, 개발자 도구에서 발견한 내부 URL은 허가의 증거가 아니다.

NAVER 행은 과거 검토 기록을 남긴 것이다. 2026-08-26 제품 결정 이후 NAVER는 실 배포 대상, fallback, 장애 시 대체 제공처로도 사용하지 않는다.

정책은 바뀔 수 있다. 위 표의 확인일 이후 실제 실행을 검토할 때에는 원문을 새로 확인해야 한다. 내장 정책 카탈로그의 검토일이 설정된 검토 유효기간(기본 7일)을 넘으면 코드가 실 요청을 차단한다. 링크가 열리지 않거나 robots.txt를 가져오지 못하는 경우에도 허용으로 간주하지 않는다.

### robots.txt 해석 원칙

robots.txt는 [Robots Exclusion Protocol(RFC 9309)](https://www.rfc-editor.org/rfc/rfc9309.html)에 따라 실제 요청 호스트와 User-Agent 기준으로 판단한다. 이 프로젝트에서는 다음과 같이 더 엄격하게 적용한다.

- `Allow`는 기술적 탐색 범위를 나타낼 뿐 이용약관, 저작권 또는 재배포 허가를 대신하지 않는다.
- `Disallow`에 해당하면 명시적인 서면 예외가 없는 한 요청하지 않는다.
- robots.txt가 없거나 404·410, 타임아웃, 5xx, 파싱 실패로 확인되지 않으면 허용으로 추정하지 않고 중단한다.
- 서면 허가가 robots.txt와 다르면, 해당 호스트·경로·User-Agent에 대한 자동 접근 예외가 허가서에 명시되어야 한다.
- 약관, 개발자 문서, robots.txt와 서면 허가 중 하나라도 더 좁은 범위를 정하면 그 좁은 범위를 따른다. 충돌이 해소되지 않으면 중단한다.
- Fargate page-only 경로는 네트워크 목적지를 정확히 두 페이지로 유지하므로 robots.txt를 런타임의 세 번째 URL로 가져오지 않는다. 대신 운영 활성화 직전 공식 원문을 수동 재확인하고, 검토 시각이 7일을 넘거나 두 경로의 서면 예외 scope가 없으면 페이지 요청 전에 차단한다. 과거 범용 CLI의 robots 캐시는 운영 허가를 대신하지 않는다.

### `api-gw.sports.naver.com`에 관한 판정

`api-gw.sports.naver.com`이라는 호스트명이나 특정 URL이 프런트엔드 코드·개발자 도구에서 관찰된 사실은 공개 API 사용권을 만들지 않는다. 응답의 200은 기술적으로 접근 가능하다는 뜻일 뿐이고, 401·403·404는 각각 인증·권한·경로 상태에 관한 결과일 뿐이다. 특히 **404 응답은 자동 수집 허가가 아니다.** 엔드포인트 추측, 경로 열거, 인증 토큰·서명·쿠키 복제 또는 차단 우회도 하지 않는다.

## 3. 데이터 범위

서면 허가가 있더라도 필요한 최소 데이터만 취급한다.

### 기본 메타데이터

허가 문서에 포함된 경우에만 다음 필드를 수집할 수 있다.

- 경기 일자와 예정 시각
- 홈팀과 원정팀의 텍스트 이름 또는 내부 정규화 코드
- 구장 텍스트 이름
- 경기 상태
- 홈·원정 점수
- 현재 이닝과 초·말
- 실제 경기 시작·종료 시각

이 값들이 사실 정보에 가깝더라도 사이트 접근 조건, 데이터베이스에 관한 권리, 계약과 재배포 제한이 별도로 적용될 수 있다. ‘사실이므로 자유롭게 크롤링할 수 있다’고 판단하지 않는다.

### 상세 이닝·relay

타자·투수 이름, 타석 결과와 같은 상세 이벤트는 기본 범위에서 제외한다. 명시적으로 허가받은 경우에도 원문의 중계 문장이나 전체 relay 응답을 보존·재현하지 않고, 필요한 최소한의 구조화 값(예: 이닝, 초·말, 이벤트 코드, 관계된 선수 이름)만 정규화한다. 원문 설명, 해설, 기사형 문장, 전체 타석 배열을 출력하거나 재배포하려면 그 사용 방식까지 별도로 허가받아야 한다.

### 명시적으로 제외되는 자산

- KBO, NAVER, 구단의 로고·엠블럼·상표
- 선수·경기 사진, 썸네일, 일러스트
- 영상, 하이라이트, GIF, 오디오와 문자중계 원문
- 광고, 기사, 해설, 댓글 등 제3자 콘텐츠
- 인증 쿠키, 세션, 토큰, 서명값과 개인정보

위 자산은 URL만 노출되어 있어도 내려받거나 캐시·프록시·임베드하지 않는다. 꼭 필요하면 각 권리자와 데이터 제공처의 별도 이용 허락을 받는다.

## 4. 허가 증빙 기준

실 네트워크 프로필을 만들기 전에 저장소 밖의 접근 제한된 장소에 다음 정보를 보관한다. 비밀, 개인정보 또는 계약 문서 원문을 Git에 커밋하지 않는다.

- 허가 주체와 담당자, 승인일, 만료일, 문서 식별자
- 허용된 도메인·경로·메서드·인증 방식
- 허용 필드와 상세 relay 포함 여부
- 초당·분당·일일 요청 한도, 동시성, 허용 시간대
- 원문 응답 및 정규화 데이터의 보관 기간
- 앱 화면 표시, 팀 내부 공유, 외부 공개와 재배포 가능 범위
- 출처 표시, 상표·로고·영상 사용 조건
- 중단·삭제 요청 연락처와 처리 기한
- 확인 당시 약관·robots.txt·개발자 문서의 URL, 확인 시각과 무결성 해시

코드에 기록하는 scope는 허가서의 실제 문구와 대응되어야 한다. KBO 일정 페이지는 `schedule-page`, 스코어보드 페이지는 `scoreboard-page`로 분리한다. robots 전체 차단에 대한 두 경로의 서면 예외는 일반 승인과 분리해 `robots-disallow-override`로 기록한다. 상세 이벤트는 현재 scope에 포함하지 않는다. scope 문자열을 추가하는 것 자체는 권한을 만들지 않으며, 항상 증빙 문서에서 같은 범위를 확인할 수 있어야 한다.

구두 승인, 메신저에서의 모호한 답변, 다른 앱이 같은 데이터를 제공한다는 사실, 과거의 허가 또는 제3자의 블로그 글은 증빙으로 인정하지 않는다. 만료 또는 범위 변경 시 실 네트워크 설정을 다시 잠근다.

## 5. 요청·부하 정책

서면 허가가 유효한 경우에도 다음 원칙을 강제한다.

- 승인된 식별 가능한 User-Agent와 연락처를 사용한다.
- 임의 쿠키·인증 헤더·URL 토큰을 설정하지 않는다. 인증이 필요한 공식 API는 별도 검토된 adapter로만 추가한다.
- 같은 호스트의 동시 요청은 1개로 제한하고, 같은 경기의 중복 요청을 합친다. 서로 다른 승인 provider만 독립적으로 병렬 처리할 수 있다.
- 예정 경기, 진행 경기, 종료 경기의 상태에 따라 폴링 간격을 늘리거나 중단한다.
- `ETag`와 `Last-Modified`가 제공되면 조건부 요청을 사용하고, 변경 없는 결과를 다시 저장하지 않는다.
- 지수 백오프와 무작위 지연을 적용하되 승인된 최대 요청량을 절대 넘지 않는다.
- `Retry-After`를 최우선으로 준수한다.
- 브라우저 자동화는 승인 범위에 브라우저 접근이 명시된 경우에만 최후 수단으로 사용한다.
- 프록시 회전, IP 우회, CAPTCHA 해제, 로그인 자동화, 숨은 경로 탐색은 금지한다.

다음 신호는 단순 오류가 아니라 **중단 신호**다.

- 401 또는 403: 재시도하지 않고 해당 제공처를 즉시 중지한다.
- 429: 같은 호출도 자동 재시도하지 않고 신규 요청을 중지하며 `Retry-After` 이상 회로를 연다. 반복되면 제공처를 비활성화하고 한도를 재협의한다.
- CAPTCHA, 봇 차단 화면 또는 명시적 경고: 즉시 전체 중단한다.
- robots.txt의 거부 또는 변경, 약관 변경, 허가 만료: 정책 검사가 통과할 때까지 중단한다.
- 5xx·타임아웃 증가: 공격적으로 재시도하지 않고 회로를 열어 장시간 휴지한다.

## 6. 저장·공개 정책

- 기본 fixture는 실제 서비스 원문을 복제하지 않은 합성 데이터여야 한다.
- 실 데이터 허가 시에도 원본 HTML·JSON 응답은 기본적으로 저장하지 않는다.
- 출력은 승인된 필드만 포함하며 출처, 관측 시각과 데이터 상태를 기록한다.
- 이벤트 로그, HTTP 헤더와 오류 로그에 쿠키·토큰·개인정보·원문 relay를 남기지 않는다.
- 보존 기한이 지나거나 허가가 철회되면 출력, 캐시, 백업, CI 산출물과 배포본에서 삭제한다.
- 외부 공개 저장소, 데모 사이트, 발표 자료로 옮기는 행위는 ‘재배포’로 보고 별도 허용 범위를 확인한다.

## 7. Kill switch와 삭제 요청

운영자는 언제든 외부 요청을 한 번에 막을 수 있어야 한다. Kill switch가 켜졌거나 상태를 확인할 수 없으면 fixture 실행만 허용한다. 제공처의 차단 신호, 정책 변경, 허가 만료, 담당자 요청 또는 예상 밖의 트래픽이 발생하면 즉시 kill switch를 켠다.

삭제·중단 요청을 받으면 다음 순서로 처리한다.

1. 전체 실 네트워크 실행과 스케줄러를 즉시 중단한다.
2. 요청 주체, 대상 제공처, 필드, 날짜 범위와 배포 위치를 기록한다.
3. 로컬 출력·상태 캐시·로그·백업·CI 산출물·배포 저장소·다운스트림 사본을 식별한다.
4. 요청 범위의 데이터와 원문 파생물을 삭제하고 재수집을 차단한다.
5. 삭제한 위치, 처리 시각, 남아 있는 법적 보존 의무만 데이터 없이 감사 기록으로 남긴다.
6. 요청자와 프로젝트 책임자에게 완료 여부를 확인한다.

자세한 점검·사고 대응 절차는 [OPERATIONS.md](./OPERATIONS.md)를 따른다.
